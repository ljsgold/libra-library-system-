# 🔧 Railway 健康检查失败排查指南

## 🎯 问题描述

当 Railway 部署显示 **"健康检查失败"**（Health check failed）时，表示应用虽然构建和部署成功，但无法通过健康检查，导致服务无法正常启动。

---

## 📊 常见错误信息

从 Railway 日志中，你可能会看到：

- ❌ **"健康检查失败"**（Health check failed）
- ❌ **"1/1的复制品从未变得健康!"**（1/1 replicas never became healthy!）
- ❌ **"尝试#X失败, 服务无法使用"**（Attempt #X failed, service unavailable）
- ❌ **"停止容器"**（Stop Container）

---

## 🔍 问题原因分析

### 1. 数据库连接失败（最常见）

**症状**：
- 健康检查运行 9-10 分钟后失败
- 日志中可能看到数据库连接错误

**原因**：
- 数据库环境变量未配置或配置错误
- 数据库服务未启动
- 数据库连接超时

**解决方案**：
1. 检查 Railway 环境变量是否正确配置（见下方"检查清单"）
2. 确认 MySQL 服务状态为 "Running"
3. 检查数据库连接字符串格式是否正确

### 2. 应用启动时间过长

**症状**：
- 健康检查超时（默认 10 分钟）
- 应用正在启动但未完成

**原因**：
- 应用首次启动需要初始化数据库连接池
- 依赖服务（如 Redis）连接超时
- 应用资源不足

**解决方案**：
1. 增加健康检查超时时间（已优化为 15 分钟）
2. 禁用非必需的健康检查（如数据库健康检查）
3. 优化应用启动配置

### 3. 健康检查端点无法访问

**症状**：
- 健康检查返回 404 或 500 错误
- 应用已启动但健康检查失败

**原因**：
- Spring Boot Actuator 未正确配置
- 健康检查路径错误
- 端口配置错误

**解决方案**：
1. 确认 `railway.json` 中的 `healthcheckPath` 为 `/actuator/health`
2. 确认 `application.yml` 中已配置 Actuator
3. 确认 `PORT` 环境变量为 `8080`

---

## ✅ 快速修复步骤

### 第一步：检查 Railway 环境变量

在 Railway 后端服务的 **"Variables"** 标签页中，确认以下变量已正确配置：

**必需变量（6 个）**：

| 变量名 | 值 | 说明 |
|--------|-----|------|
| `SPRING_PROFILES_ACTIVE` | `mysql` | 使用 MySQL 数据库 |
| `SPRING_DATASOURCE_URL` | `jdbc:mysql://${{MySQL.MYSQLHOST}}:${{MySQL.MYSQLPORT}}/${{MySQL.MYSQLDATABASE}}?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=UTC` | 数据库连接地址 |
| `SPRING_DATASOURCE_USERNAME` | `${{MySQL.MYSQLUSER}}` | 数据库用户名 |
| `SPRING_DATASOURCE_PASSWORD` | `${{MySQL.MYSQLPASSWORD}}` | 数据库密码 |
| `JWT_SECRET` | `libra-bms-secret-key-libra-bms-secret-key-libra-bms` | JWT 密钥 |
| `PORT` | `8080` | 应用端口 |

**重要提示**：
- `${{MySQL.XXX}}` 是 Railway 的特殊语法，会自动替换为真实的数据库连接信息
- 如果变量值不正确，请参考 `docs/快速部署.md` 中的详细说明

### 第二步：检查 MySQL 服务状态

1. 在 Railway 项目中，点击 **MySQL 服务**（不是后端服务）
2. 查看服务状态：
   - ✅ **"Running"**（绿色）= 正常运行
   - ❌ **"Stopped"** 或 **"Error"** = 需要修复

3. 如果 MySQL 服务未运行：
   - 点击 **"Settings"** → **"Redeploy"** 重新部署
   - 或点击 **"Deployments"** 查看部署日志

### 第三步：检查应用日志

1. 在 Railway 后端服务页面，点击 **"Logs"** 标签页
2. 查看最近的日志，查找错误信息：

**常见错误及解决方案**：

| 错误信息 | 原因 | 解决方案 |
|---------|------|---------|
| `Connection refused` | 数据库连接失败 | 检查环境变量 `SPRING_DATASOURCE_URL` |
| `Table doesn't exist` | 数据库未初始化 | 执行 `db/init.sql` 脚本 |
| `Access denied` | 数据库认证失败 | 检查 `SPRING_DATASOURCE_USERNAME` 和 `SPRING_DATASOURCE_PASSWORD` |
| `Port already in use` | 端口冲突 | 确认 `PORT` 环境变量为 `8080` |
| `OutOfMemoryError` | 内存不足 | 增加 Railway 服务资源或优化应用配置 |

### 第四步：测试健康检查端点

1. 在 Railway 后端服务页面，点击 **"Settings"** 标签页
2. 在 **"Domains"** 部分，找到你的后端域名
3. 在浏览器中访问：`https://你的后端域名/actuator/health`
4. **预期结果**：
   - ✅ 返回 JSON：`{"status":"UP"}` = 健康检查正常
   - ❌ 返回 404 = 健康检查路径错误
   - ❌ 返回 500 = 应用启动失败
   - ❌ 无法访问 = 服务未运行

### 第五步：重新部署

如果修改了环境变量或配置，需要重新部署：

1. 在 Railway 后端服务页面，点击 **"Deployments"** 标签页
2. 找到最新部署，点击 **"..."** → **"Redeploy"**
3. 等待部署完成（约 5-10 分钟）
4. 观察部署日志，确认健康检查是否通过

## 🔧 已优化的配置

为了减少健康检查失败，我已经优化了以下配置：

### 1. 禁用数据库健康检查

**文件**：`libra-admin/src/main/resources/application.yml`

```yaml
management:
  health:
    db:
      enabled: false  # 禁用数据库健康检查，避免数据库连接问题导致健康检查失败
```

**原因**：数据库连接问题可能导致健康检查失败，即使应用已正常启动。禁用数据库健康检查后，健康检查只检查应用是否启动，不检查数据库连接。

### 2. 增加健康检查超时时间

**文件**：`railway.json`

```json
{
  "deploy": {
    "healthcheckTimeout": 900,  // 从 600 秒（10分钟）增加到 900 秒（15分钟）
    "healthcheckInterval": 15   // 从 10 秒增加到 15 秒
  }
}
```

**原因**：应用首次启动可能需要较长时间初始化数据库连接池和依赖服务，增加超时时间可以给应用更多启动时间。

## 💡 常见问题解答

### Q1: 为什么禁用数据库健康检查？

**A:** 数据库健康检查会在应用启动时尝试连接数据库。如果数据库连接有问题（如网络延迟、连接池初始化慢），即使应用已正常启动，健康检查也会失败。禁用数据库健康检查后，健康检查只检查应用是否启动，不检查数据库连接，这样可以避免因数据库连接问题导致的健康检查失败。

### Q2: 健康检查超时时间应该设置多少？

**A:** 建议设置为 15 分钟（900 秒）。如果应用启动时间超过 15 分钟，可能需要：
1. 优化应用启动配置
2. 检查是否有阻塞的初始化操作
3. 增加 Railway 服务资源

### Q3: 如何确认应用是否真的启动成功？

**A:** 除了健康检查，你还可以：
1. 访问 Swagger 文档：`https://你的后端域名/swagger-ui.html`
2. 查看应用日志，确认没有错误信息
3. 尝试调用一个简单的 API 接口

### Q4: 健康检查失败后，应用会自动重启吗？

**A:** 是的。Railway 配置了 `restartPolicyType: "ON_FAILURE"`，如果健康检查失败，Railway 会自动重启应用。但如果问题持续存在（如环境变量配置错误），应用会不断重启失败。
